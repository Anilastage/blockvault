================================================================================
  BlockVault — DEPLOYMENT PLAYBOOK
  What to do BEFORE, DURING, and AFTER deploying to production
================================================================================

  Stack at a glance (for reference)
  - Backend  : Node 20 + Express + TypeScript, compiled to dist/server.js
  - Database : MongoDB (dev currently uses MongoDB Atlas URI in backend/.env)
  - Frontend : React 18 + Vite, served by nginx which reverse-proxies /api
              to the backend (SSE needs proxy_buffering off — already set
              in frontend/nginx.conf)
  - Blockchain: Hardhat + DocumentVerification.sol. Local chain = 31337,
              public testnet target = Sepolia (11155111)
  - Docker   : docker-compose.yml runs mongo + backend + frontend

  IMPORTANT CURRENT DEFAULTS THAT MUST NOT GO TO PROD
  - docker-compose.yml falls back JWT_SECRET to "change-me-to-a-long-random-string".
    The backend env.ts refuses a fallback in production (good), but if you use
    compose you MUST pass a real JWT_SECRET, or startup will still complain.
  - backend/.env currently has a dev JWT secret, a shared Gmail app password,
    RPC URL 127.0.0.1:8545 and contract on chain 31337. Do NOT ship these.


================================================================================
  PHASE 1 — BEFORE DEPLOYING  (do all of these, in order)
================================================================================

[ ] 1. Verify everything still builds & passes
        cd backend && npm run typecheck
        cd backend && npm test                 (33 tests expected)
        cd blockchain && npm test
        cd frontend && npm run typecheck
        npm run build                          (root: builds backend + frontend)
      Fix any failure before touching production.

[ ] 2. Prepare production secrets
        - JWT_SECRET: generate one long random value per environment, e.g.
            node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"
        - Put secrets in your host .env / secret manager. NEVER in git.

[ ] 3. MongoDB — production instance
        - Either keep Atlas (current URI) or run your own mongod with auth.
        - Enable authentication + a dedicated app user with least privilege.
        - Turn ON backups (Atlas continuous backup or daily mongodump + retention).
        - If using docker-compose's mongo service, also set a password and
          MONGODB_URI=mongodb://user:pass@mongo:27017/blockvault.
        - Run a test backup & restore BEFORE going live.

[ ] 4. Email (SMTP) — required, login is gated on Email OTP
        - Current creds are a Gmail account (app password).
        - For production prefer a domain sender (SendGrid, SES, Zoho, Mailgun…).
        - Set up SPF / DKIM / DMARC for your domain so OTP emails don't land in
          spam. Gmail free accounts cap ~500 emails/day — this project emails
          one OTP per login, so be aware of the ceiling.
        - Values: SMTP_HOST, SMTP_PORT, SMTP_USER, SMTP_PASS,
                  EMAIL_FROM_NAME, EMAIL_FROM_ADDRESS
        - If you have a Twilio number, SMTP_CONFIDENTIAL: TWILIO_ACCOUNT_SID,
          TWILIO_AUTH_TOKEN, TWILIO_FROM_NUMBER (optional; SMS OTP feature).

[ ] 5. Blockchain — deploy the contract to Sepolia
        - Fill blockchain/.env with:
            SEPOLIA_RPC_URL   (Infura / Alchemy / Alchemy free tier)
            DEPLOYER_PRIVATE_KEY (a funded testnet wallet — hold enough Sepolia ETH)
            ETHERSCAN_API_KEY (optional, for verification)
        - Deploy and verify:
            cd blockchain
            npm run deploy:sepolia            # writes deployment.json
        - Record the deployed CONTRACT_ADDRESS.
        - Confirm the deployed address on Etherscan (or your explorer).

[ ] 6. Prepare the backend environment (production values)
        NODE_ENV=production
        PORT=5000
        MONGODB_URI=...                        (see step 3)
        JWT_SECRET=...                         (see step 2 — REQUIRED in prod)
        JWT_EXPIRES_IN=7d
        CLIENT_URL=https://app.yourdomain.com  (comma-separated list of origins;
                                               must match your real origin or CORS
                                               will block the browser)
        BLOCKCHAIN_RPC_URL=https://sepolia...  (public Sepolia RPC / your provider)
        CHAIN_ID=11155111
        CONTRACT_ADDRESS=0x...                 (from step 5)
        BLOCKCHAIN_EXPLORER_URL=https://sepolia.etherscan.io
        SMTP_* , EMAIL_FROM_*                  (from step 4)
        TWILIO_*                               (only if SMS OTP used)

[ ] 7. Prepare the frontend build
        - VITE_API_URL: keep "/api" when served behind the nginx container
          (same-origin reverse proxy, no CORS). Only set an absolute URL if the
          API is hosted on another origin.
        - The nginx config already handles SPA fallback + SSE proxy.
        - Decide your TLS strategy now (see Phase 2 step 9).

[ ] 8. Admin account plan
        - The FIRST user to register becomes ADMIN (authController.ts).
        - Either register that admin during go-live, or promote an existing user:
            cd backend && npm run dev  /  node dist/...
            node dist/scripts...  -> use backend/scripts/promote.ts:
            npx tsx scripts/promote.ts you@domain.com   (run against prod DB)
        - Verify /api/admin routes accept that account.

[ ] 9. File persistence for uploads
        - Uploads are stored under backend/uploads (Docker volume "uploads").
        - Back it up; expected 10 MB max per file (env.ts upload.maxFileSizeMb).
        - Note: the container never serves uploads statically — all downloads
          go through authorized routes, so the volume is not public.

[ ] 10. Domain + HTTPS plan
        - Decide: api.yourdomain.com along with app.yourdomain.com, or a single
          origin with /api proxied (recommended — nginx already does this).
        - Reserve DNS records; plan TLS certs (Let's Encrypt / cert-manager /
          Cloudflare / your cloud LB).

[ ] 11. Rollback + safety
        - Tag every release (git tag vX.Y.Z) and keep the last known-good image.
        - Snapshot the empty/current DB before first go-live so you can start clean.


================================================================================
  PHASE 2 — DURING DEPLOYING  (execute in order)
================================================================================

[ ] 12. Provision the host
        - Node 20 not needed on the host if you use Docker; needed if you run
          node directly (backend: node dist/server.js, start script exists).

[ ] 13. Put the code + secrets on the server
        - git clone / pull your repo at a tagged release.
        - Create the production .env files that are git-ignored:
            backend/.env      (step 6)
            blockchain/.env   (step 5)
        - DO NOT copy the dev .env (contains local RPC + personal Gmail).

[ ] 14. Build & start containers
        - docker compose build --no-cache
        - docker compose up -d
        - Verify containers: docker compose ps
        - Watch logs during startup:
            docker compose logs -f backend      (expect "BlockVault API running")
            docker compose logs -f mongo        (expect healthy; healthcheck set)
        - If you skipped containerized mongo (using Atlas), comment that service
          out / just run backend+frontend.

[ ] 15. Confirm the contract wiring (if you deployed to Sepolia)
        - backend must log the startup line and NOT warn
          "CONTRACT_ADDRESS not set".
        - Set CONTRACT_ADDRESS + BLOCKCHAIN_RPC_URL + CHAIN_ID=11155111 and
          restart the backend container if they were added after boot.

[ ] 16. First-boot data checks
        - Ensure Mongo collections are created; verify read/write to the app DB.
        - Register the first admin account now (or run promote.ts, step 8).

[ ] 17. Point DNS / set CLIENT_URL to the live origin
        - Once the host IP is live, point your DNS A/AAAA records.
        - Make sure CLIENT_URL exactly matches the origin the browser uses
          (scheme + hostname + optional port), otherwise CORS rejects requests.

[ ] 18. Enable HTTPS when ready
        - Preferred: terminate TLS on the nginx frontend container (add a
          certbot/caddy sidecar or swap the frontend image for an ingress that
          handles TLS), and/or put everything behind a managed load balancer.
        - Redirect HTTP -> HTTPS; enable HTTP/2.
        - Frontend serves on :8080 (mapped to 80 inside); keep that internal
          and only expose :443 to the internet.

[ ] 19. Final smoke test on the LIVE url (see Phase 3 — repeat the checklist
         against https://app.yourdomain.com, NOT localhost).


================================================================================
  PHASE 3 — AFTER DEPLOYING  (verify, then operate)
================================================================================

[ ] 20. Automated release gate (recommended afterwards)
        - The repo has .github/workflows (empty) — wire CI to run:
            backend typecheck + tests, blockchain tests, frontend build
          on every push/PR BEFORE merge.

[ ] 21. Full functional smoke test (do this first time and after each release)
        - GET  https://app/health                          -> 200 success
        - Register first user                            -> role ADMIN
        - Login (password)                               -> Email OTP delivered?
             -> ONLY rely on devCode if SMTP is off — in prod the code arrives
                by email; if no email arrives, check spam + SMTP logs.
        - Enable TOTP 2FA, log in again using the 6-digit email OTP + TOTP.
        - Upload a document                              -> file appears, hash computed
        - Register document on-chain                     -> transactionHash set,
             then view it on the explorer link configured
        - Verify a document by upload / by code          -> VERIFIED status + chain lookup
        - Share link / share download code               -> recipient flow works
        - Download as owner, as admin, via code, via access request
        - Admin dashboard, analytics, activity logs, transactions list
        - Wallet connect in the browser (MetaMask on Sepolia) if using web3 features
        - SSE notifications: open the app in another tab and trigger a
          notification (e.g., access request) — banner must appear live.

[ ] 22. Monitoring & operations
        - Health/uptime: poll /health (200 + message).
        - Logs: docker compose logs; watch for 429s (rate limits are on),
          5xx, and SMTP send errors.
        - Storage: keep an eye on the uploads volume size.
        - Rate limiting already covers /api (300/min/IP), auth (authLimiter),
          OTP (per-user), downloads (downloadLimiter) — no action needed,
          just know the knobs exist in middleware/rateLimiter.ts.
        - Backups: schedule a nightly mongodump or use managed DB backups;
          test restore at least once a month.

[ ] 23. Security checklist AFTER go-live
        - Confirm JWT_SECRET is a long random value in prod (no fallback string).
        - Confirm devCode is NEVER returned in prod (authController keeps it
          behind !isEmailConfigured() && NODE_ENV !== test — verify by looking
          at a login response).
        - Rotate the Gmail app password if the dev .env ever touched a repo.
        - TLS cert auto-renewal is configured.
        - Mongo is only reachable from the backend, not from the internet
          (Atlas: allowlist host IP; self-hosted: firewall port 27017).

[ ] 24. When you scale later
        - Move to managed Mongo first; uploads should go to object storage (S3)
          since the local Docker volume can't be shared across replicas.
        - Multiple backend replicas need a shared session/notifications store
          (notifications are currently in-memory via SSE).
        - Keep SSE behind a proxy with buffering OFF (already done in nginx.conf).

[ ] 25. Rollback procedure (if a release misbehaves)
        - docker compose down
        - Restore the previous tagged image / git tag
        - docker compose up -d   (env vars unchanged)
        - If the DB was migrated forward and the rollback needs the old schema,
          restore the pre-release backup (backup before every deploy).
